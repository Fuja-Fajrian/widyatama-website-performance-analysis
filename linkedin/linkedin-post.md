# LinkedIn Post

I recently completed a portfolio project on **website performance and technical SEO analysis** for the PMB Universitas Widyatama website.

The project started with a broad crawl and was narrowed into an analytical workflow that could support decision-making rather than just produce a list of technical issues.

Key scope:
- 627 internal URLs discovered during the initial crawl
- 119 internal HTML URLs retained for the main audit
- 174 PageSpeed API observations
- 87 pages represented in the PageSpeed baseline
- 43 pages used for targeted smoke-test validation

My workflow:

**Site Crawl → Page-Level Data → Performance Diagnostic → Root Cause Analysis → Template Analysis → Prioritization → Remediation Backlog → Dashboard**

The main learning for me was that web performance analysis becomes much more useful when the findings are grouped into recurring patterns and translated into priorities. Instead of stopping at “this page is slow,” the analysis asks what resource, template, or technical behavior is repeatedly contributing to the problem and how that should influence remediation order.

For this portfolio release, I intentionally stop at the **analysis + dashboard** stage so the project clearly demonstrates the analytical process, evidence structure, and communication of findings.
